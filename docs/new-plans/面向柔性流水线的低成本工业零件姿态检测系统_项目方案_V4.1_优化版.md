# 1. V4 的核心变化

V4 不再继续扩张大量高级功能，而是把项目收缩成一条更接近工业生产检测的验证主线：

    能不能看准
    ↓
    能不能稳定判断
    ↓
    不确定时能不能安全拒绝
    ↓
    换一个产品到底有多麻烦

项目从“功能清单驱动”调整为“假设验证驱动”。

V3.1 中已有的 Recipe、Tracking、Multi-frame、Decision Zone、UNCERTAIN、Hard Sample、Domain Shift 等能力仍然保留，但重新划分优先级。

V4 的原则是：

> 少增加功能，多增加可复现、可比较、可量化的实验结论。

V4.1 不改变 V4 的四条核心主线，不新增大型功能模块。优化重点从“系统能力设计”转向“实验协议冻结”，正式补齐：

- Operating Envelope（适用工况边界）；
- Ground Truth Protocol（事件级真值协议）；
- Traditional CV Fairness Protocol（公平对照协议）；
- Statistical Reporting Protocol（统计可信度协议）；
- Risk-Coverage-Latency 三目标权衡；
- Part A / Part B 预冻结与换型实验防偏置规则。

V4.1 的目标是：

> **在正式训练之前先冻结“怎么证明”，再开始证明“能不能做到”。**

# 2. 项目一句话定位

> 使用普通 RGB 相机、消费级 GPU 和开源轻量 OBB 模型，研究低成本工业零件姿态视觉在精度、稳定性、风险控制和柔性换型方面能够达到什么水平，以及它相对于传统视觉和商业工业视觉的适用边界。

# 3. 项目边界

V4 明确不把以下事项作为主要交付：

- 不追求功能数量最多；
- 不追求完整 3D Vision；
- 不追求真实机器人闭环控制；
- 不追求真实 PLC / 气动剔除机构；
- 不追求复杂 Open-set Recognition；
- 不追求论文级 Active Learning Framework；
- 不追求复杂 Feature-level Domain Adaptation；
- 不宣称替代 KEYENCE、Cognex、Epson、Asyril 等成熟工业系统；
- 不宣称达到 24/7 工业生产级可靠性。

这些能力保留为 Future Work 或工业化扩展方向。

## 3.1 Operating Envelope — 正式适用工况边界

V4.1 增加一个必须在正式验收前冻结的 Operating Envelope。

项目的任何性能结论都必须绑定到明确工况，不允许使用“适用于工业流水线”这种无边界表述。

至少记录：

- Camera：设备、分辨率、FPS、曝光策略、相机高度 / 距离；
- Field of View：有效检测区域与目标像素尺寸范围；
- Part：Part A / Part B、尺寸、Front / Back 定义、允许姿态范围；
- Motion：静态、低速、目标速度范围或等效运动条件；
- Spacing：零件最小间距、是否允许遮挡 / 重叠；
- Lighting：正常光、暗光、强反光；可测时记录照度，否则记录曝光和图像亮度统计；
- Background：基准背景及允许的背景变化；
- Blur / Occlusion：进入正式测试的扰动等级。

最终结论必须写成：

> 在已冻结的 Operating Envelope 内，本系统达到某项性能。

超出边界时只能报告实验观察，不能外推为生产能力。

# 4. V4 的四条核心主线

## 4.1 Lightweight Perception — 轻量感知

核心流程：

    YOLO26n-OBB
    ↓
    Part Identity
    + Front / Back
    + OBB
    + Center
    + 2D Orientation

研究重点：

> 单个轻量 OBB 模型能否同时完成零件身份、正反面与二维姿态检测，并在消费级 GPU 上达到可接受的实时性。

## 4.2 Reliable Event Decision — 事件级稳定决策

不直接把每一帧 YOLO 输出作为生产结果。

    Detection
    ↓
    Tracking
    ↓
    Multi-frame Evidence
    ↓
    Decision Zone
    ↓
    Single-Part Event

研究重点：

> 相比单帧预测，事件级决策能否减少类别抖动、角度抖动、重复计数和错误单件事件。

## 4.3 Risk-Aware Rejection — 风险拒绝

最终状态：

    PASS
    FAIL_FACE
    FAIL_ORIENTATION
    UNCERTAIN

研究重点：

> 允许系统拒绝一部分证据不足的样本后，Wrong Accept Rate 能降低多少，代价是多少 Coverage。

## 4.4 Flexible Changeover — 柔性换型

通过：

    Recipe
    + Dataset
    + Fine-tune

实现 Part A → Part B。

研究重点：

> 新增一种零件时，需要多少采集、标注、训练、配置和代码改动。

# 5. V4 的四个核心研究问题

## RQ1 — AI 是否真的值得使用

比较：

    Traditional CV Baseline
    vs
    YOLO26n-OBB
    vs
    YOLO26s-OBB

回答：

- 传统模板 / 轮廓方法是否已经足够；
- YOLO 对光照、旋转和外观变化的收益是多少；
- Nano 与 Small 谁更适合本任务。

## RQ2 — 为什么不能直接逐帧检测

比较：

    Single Frame
    vs
    Tracking + Multi-frame + Decision Zone

回答：

- Wrong Accept 是否下降；
- Face Flip 是否减少；
- Angle Jitter 是否降低；
- Duplicate Event 是否减少；
- Missed Event 是否变化。

## RQ3 — UNCERTAIN 是否真正降低生产风险，以及代价是多少

通过阈值扫描生成：

    Coverage vs Wrong Accept Rate vs End-to-End P95 Latency

回答：

> 为了降低错误放行，需要牺牲多少自动处理率，以及多帧稳定决策增加了多少端到端延迟。

## RQ4 — “柔性换型”是否真的成立

真实执行 Part A → Part B，记录：

- 新增图像数量；
- 有效标注数量；
- 标注分钟；
- Fine-tune 时间；
- Recipe 修改；
- 主程序代码修改；
- Part B 最终性能；
- Part A Regression。

# 6. V4 最重要的工业 KPI

## 6.1 第一核心 KPI：Wrong Accept Rate

定义：

> 实际应该 FAIL / UNCERTAIN 的零件，被系统最终放行为 PASS 的比例。

示例：

    实际：BACK
    系统：PASS
    → Wrong Accept

这是项目最重要的生产风险指标。

## 6.2 第二核心 KPI：Wrong Reject Rate

定义：

> 实际合格零件，被系统判为 FAIL 或 UNCERTAIN 的比例。

它反映生产效率损失。

## 6.3 第三核心 KPI：Coverage

定义：

> 系统能够自动给出明确 PASS / FAIL 的样本比例。

    Coverage = 1 - UNCERTAIN Rate

## 6.4 第四核心 KPI：End-to-End P95 Latency

必须测完整链路：

    Capture
    ↓
    Preprocess
    ↓
    Inference
    ↓
    Tracking
    ↓
    Evidence Aggregation
    ↓
    Decision
    ↓
    Event Output

而不是只报告模型 inference FPS。

## 6.5 第五核心 KPI：Changeover Cost

统一记录：

- New Images；
- Annotation Minutes；
- Fine-tune Minutes；
- Recipe Changes；
- Code Changes；
- Total Changeover Time；
- Old-Part Regression。

## 6.6 第六核心要求：Statistical Reliability

V4.1 规定所有核心风险指标不能只报告一个百分比。

Wrong Accept、Wrong Reject、Coverage、Missed Event、Duplicate Event 至少同时报告：

- numerator / denominator；
- event sample count `n`；
- point estimate；
- 95% confidence interval。

比例指标默认使用 Wilson 95% CI；若出现 0 次错误，不允许只写 `0%`，必须同时报告样本量与上置信界。

可使用“rule of three”作为零事件的直观解释：若 `n` 个独立相关事件中 0 次错误，则 95% 上界约为 `3/n`。

因此：

> **0/20 与 0/1000 不是同一个证据等级。**

Latency 至少报告样本量、Median、P95；条件允许时补充 P95 bootstrap CI。

# 7. 传统 CV Baseline

V4 新增一个正式对照组，用来回答：

> 对当前零件任务，是否真的需要深度学习？

根据 Part A 结构选择最简单的可行方法：

- Template Matching；
- Contour Matching；
- Shape Descriptor；
- Threshold + Morphology；
- PCA / minAreaRect Angle；
- 简单 Rule-based Front / Back Feature。

V4 不要求把传统方法做成复杂工业视觉平台，只要求建立一个可复现 Baseline。

## 7.1 Fairness Protocol — 公平对照原则

Traditional CV 与 YOLO 必须在同一测试协议下比较：

- 相同 Camera / Video 输入；
- 相同分辨率；
- 相同 ROI；
- 相同 Test Events；
- 相同 Operating Envelope；
- 相同计时起点 / 终点定义；
- 所有阈值只允许在 Train / Val 或 Calibration Set 上调整；
- Test Set 不用于调参；
- Traditional CV 参数在最终 Test 前冻结；
- YOLO confidence / NMS / decision threshold 同样在最终 Test 前冻结。

比较目的不是“证明 AI 一定更好”，而是确定各方法在什么工况下更合适。

比较维度：

| 指标 | Traditional CV | YOLO26n-OBB | YOLO26s-OBB |
| --- | ---: | ---: | ---: |
| Face Accuracy | 实测 | 实测 | 实测 |
| Wrong Accept | 实测 | 实测 | 实测 |
| Angle MAE | 实测 | 实测 | 实测 |

# 9. 姿态语义与适用边界

## 9.1 基础 OBB 角度

默认：

θ ∈ [0°,180°)

对于普通长轴件，θ 与 θ+180° 等价。

## 9.2 Symmetry-aware Angle

Recipe 中保留 symmetry_order。

评价周期：

    period = 360 / symmetry_order

只有零件真实结构支持时才使用。

## 9.3 Near-square Failure Guard

V4 正式增加：

> 不是所有零件都适合用 OBB 长轴表达姿态。

对于 width ≈ height，OBB 主轴可能不稳定。

Recipe 建议：

    orientation:
      mode: axial
      min_aspect_ratio: 1.25

若：

    max(w,h) / min(w,h) < min_aspect_ratio

则：

    orientation = UNDEFINED
    decision = UNCERTAIN

而不是强制输出一个不可靠角度。

# 10. Event Decision

状态机：

    NEW
    ↓
    OBSERVING
    ↓
    STABLE
    ↓
    ENTER_DECISION_ZONE
    ↓
    DECIDED
    ↓
    COMPLETED

异常：

    OBSERVING
    ↓
    UNCERTAIN
    ↓
    REVIEW / REJECT

原则：

> 1 Track → 1 Final Event。

多帧证据包括：

- Face Votes；
- Mean Confidence；
- Angle Mean；
- Angle Std；
- Track Age；
- Valid Frame Count。

# 11. UNCERTAIN 决策

UNCERTAIN 不是训练类别，而是 Decision Layer 输出。

触发来源包括：

- Confidence 过低；
- Face 多帧意见分裂；
- Angle Std 过高；
- Near-square；
- Track 生命周期过短；
- Occlusion；
- Missed Frames；
- Domain Warning；
- 无法形成稳定证据。

# 12. Risk-Coverage-Latency Experiment

扫描多个风险阈值。

| Reject Rate | Coverage | Wrong Accept | Wrong Reject | End-to-End P95 |
| ---: | ---: | ---: | ---: | ---: |
| 0% | 100% | 实测 | 实测 | 实测 |
| 2% | 98% | 实测 | 实测 | 实测 |
| 5% | 95% | 实测 | 实测 | 实测 |
| 10% | 90% | 实测 | 实测 | 实测 |

同时扫描：

- confidence；
- min_stable_frames；
- face agreement；
- max_angle_std_deg。

每一个工作点都必须形成四元组：

    (Wrong Accept, Wrong Reject, Coverage, End-to-End P95)

优先观察 Pareto-efficient 工作点，不允许只选择“看起来最好”的单一指标。

最终工作点必须在 Validation / Calibration 数据上冻结，最终 Test 只做一次正式报告，避免测试集反复调参。

最终回答：

> Wrong Accept 每下降一个等级，需要牺牲多少 Coverage，以及会增加多少事件级决策延迟。

# 14. Changeover Cost Experiment

Part A 作为初始产品。

V4.1 要求在 Part A 正式训练前，同时预冻结 Part B 的选择原则与候选实物，避免在看到 Part A 结果后再挑选“最容易成功”的 Part B。

Part A / Part B 选择要求：

- 都属于二维平面姿态检测任务；
- 都存在可操作的 Front / Back 或明确方向语义；
- Part A 优先选择 OBB 长轴稳定、适合建立基线的零件；
- Part B 应在外形、纹理、尺寸或正反面差异上与 Part A 有明显不同；
- Part B 仍应落在本项目 Operating Envelope 内；
- 不为了提高成功率，在实验中途替换 Part B。

Part B 在 Phase 5 才进入正式数据采集、Fine-tune 与验收，但对象本身应在 Phase 1 冻结。

# 19. 数据策略

Part A 必须来自项目自建真实数据，并至少覆盖：

- Front；
- Back；
- 多角度；
- 多位置；
- 正常光；
- 暗光；
- 强反光；
- 背景变化；
- 运动模糊；
- 部分遮挡。

禁止把同一视频连续帧随机拆分到 train / val / test。

使用：

    Session A → Train
    Session B → Val
    Session C → Test

其中：

- Train：训练模型或拟合 Traditional CV 参数；
- Val / Calibration：选择模型、阈值、Risk Gate 工作点；
- Test：最终冻结评估，不用于任何形式的调参。

如果后续使用 Hard Sample 重新训练，禁止把最终 Test 错误样本直接回流到训练集后继续沿用同一 Test 作为“新模型最终测试”。应保留独立 Final Holdout，或重新建立未见过的最终测试 Session。

## 19.1 Ground Truth Protocol

V4.1 的核心指标以“单件事件”为统计单位，因此必须建立事件级 Ground Truth。

每个正式测试 Event 至少记录：

- event_gt_id；
- part_id；
- true_face；
- true_orientation_deg 或 orientation_valid=false；
- expected_decision；
- session_id；
- condition_id；
- reviewer；
- review_status。

Ground Truth 原则：

1. Face GT 由实物正反面定义产生，并在采集前冻结判据；
2. Angle GT 优先使用物理角度基准板 / 固定治具产生；无法使用治具时，采用人工 OBB 标注并进行第二次复核；
3. Event GT 以零件为单位，而不是逐帧投票结果；
4. 有争议或无法定义的样本不能强制作为确定 GT，应单独标记并从主指标中分层报告；
5. Ground Truth 修改必须版本化并保留变更记录。

## 19.2 Test Condition Matrix

测试数据必须绑定 `condition_id`，至少区分：

- nominal；
- low_light；
- reflection；
- background_shift；
- motion_blur；
- partial_occlusion。

最终结果既报告 Overall，也报告分工况结果，避免平均值掩盖某一类明显失效。

## 20.1 Formal Reporting Protocol

- 报告失败样本，不只展示成功 Demo；
- 核心比例指标报告 `x / n` 与 95% CI；
- 性能结论同时给出 nominal 与 stress-condition 分层结果；
- 不把官方 benchmark 当成本项目结果；
- 不把 Validation 结果写成 Final Test；
- 如果实验假设未被支持，按真实结果记录，不临时修改假设来追求“成功”。

# 27. V4 成功标准

V4 不用“实现了多少功能”判断成功。

项目需要得到以下四个明确结论。

## H1

> YOLO26n-OBB 相比 Traditional CV 在指定复杂条件下是否具有明确收益。

结果可以是支持、部分支持或不支持。

## H2

> Event Decision 是否相比 Single Frame 降低单件错误率和抖动。

## H3

> UNCERTAIN 是否能以可接受的 Coverage 与 End-to-End P95 Latency 代价降低 Wrong Accept。

## H4

> Part B 是否能够主要通过 Dataset + Fine-tune + Recipe 完成换型，而无需重写核心系统。

即使某个假设被否证，只要实验严谨，仍然是有效项目结论。

# 31. 理想最终结论模板

最终报告不应该只写：

> 模型准确率 97%。

而应该形成类似：

> 在普通 RGB 相机与 RTX 4060 Laptop 平台上，YOLO26n-OBB 对目标零件实现了 X% Face Accuracy、Y OBB mAP50 与 Z° Angle MAE。相比传统视觉方法，在光照或旋转变化条件下 Wrong Accept 从 A 降低到 B，但计算延迟增加 C ms。
>
> 在连续视频中，Tracking + Multi-frame + Decision Zone 将单件 Wrong Accept 从 D 降低到 E，并将 Duplicate Event Rate 从 F 降低到 G。
>
> 通过 UNCERTAIN Risk Gate，在保持 H% Coverage 且 Event P95 为 P ms 时，Wrong Accept 进一步降低至 I，并报告对应 95% CI。
>
> 在 Part B 换型实验中，新系统需要 J 张图片、K 分钟标注和 L 分钟 Fine-tune，核心代码修改 M 行 / 0 行，并达到 N 的目标性能。
>
> 因此，本项目证明或部分证明了消费级硬件与开放轻量视觉模型在特定二维柔性流水线姿态检测场景中的可行性，同时明确了其在几何、鲁棒性与工业硬件方面的边界。

# 34. V3.1 / V4 / V4.1 关系

你在比较 V3.1、V4 与 V4.1 时，可以重点看五个问题：

1. 哪一版更容易在课程周期内完整做完？
2. 哪一版更容易拿出真实实验数据？
3. 哪一版面对“市场早已有类似系统”时更容易解释自己的价值？
4. 哪一版更接近工业生产真正关心的错误率、延迟和换型成本？
5. 哪一版更容易形成一个逻辑完整、证据充分的最终答辩？

V3.1 更像“完整开放工业视觉平台蓝图”。

V4 完成了从功能导向到假设验证导向的收缩。

V4.1 则进一步冻结“证据如何产生”，把 Operating Envelope、Ground Truth、公平对照、统计可信度和 Risk-Coverage-Latency 纳入正式实验协议。

正式开发采用 V4.1；V3.1 作为长期 Roadmap，V4 作为设计演进记录保留。
